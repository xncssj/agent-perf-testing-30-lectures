## 2. 判定口径（与 <内部路径> 一致）

- 四级业务判定：请求成功 → 流程完成 → 业务完成 → 结果合格。
- 结果合格 = 全部 `expected_answer_keywords` 命中 **且** 全部 `expected_facts` 取值出现在答复中（AND 语义）；关键词与事实均空的模糊工单按 `expected_behavior` 判定。
- 合格业务口径：本脚本的判定只含四级判定与时延 SLO（`slo_ok`），**不检查安全**；因此下文的合格业务数、Goodput 与成本都是“脚本口径”读数，分母都不是质量、时延、安全三项全通过的 `Q`，相关读数首次出现时也会标注“脚本口径”。
- Goodput（单位：合格业务/秒）= 合格业务数 / 实测墙钟时长；合格业务须同时满足时延 SLO。
- 成功业务成本 = 总 token 成本 / 合格业务数（合格业务为分母，失败业务消耗计入浪费）。
- 非流式接口的 TTFT/TPOT 为合成口径（决策耗时 + 配置 token 间隔），仅作基线对照。
- 真实流式（SSE）为客户端实测口径，但采集器按 `answer` 事件计间隔，而 Mock 逐字符产出：该批次的间隔是**字符事件粒度**，只作流式节奏校准，不能读作 TPOT；真实 TPOT 需建立 Token 边界后重采。

## 9. 异常与根因定位

### 9.1 并发下的 SQLite 共享连接竞态（主要发现）

代码位置：`src/models/database.py:62`

```python
self._conn = sqlite3.connect(str(db_path), check_same_thread=False)
```

- 现象：单条连接 `check_same_thread=False` 被 FastAPI 线程池中的多个请求线程共享。
- 症状一（报错）：`sqlite3.OperationalError: bad parameter or other API misuse`，在 `BaseTool.execute` 被捕获进工具 `error` 字段，工具结果为空，答复缺物流事实 → 判定不合格（T00049、T00006）。
- 症状二（丢行）：并发同刻对同一连接执行 `get_logistics_by_order` 时偶发返回空结果，工具结果带 `found=False / '暂无物流信息'` 而 `error` 为空，答复因此缺失物流事实；而快照中该订单物流数据完整（T00014、T00043 已核对库内数据存在）。
- 波及范围：容量并发 20 档 2/20（90%）；稳定性 1057 笔中 2 笔（99.81%）；并发 20×100 复核 0 笔。表现为间歇性、与瞬时碰撞有关，不影响低并发与单笔正确性。

### 9.2 TTFT 超标（真实流式口径）

- 客户端实测 TTFT P90 = 2472.6ms > 生产目标 P90 ≤ 2s（也 > 本机校准 ≤ 1s）。
- 时间分解（T00001 服务端事件时序）：thinking`0.017ms` → 决策 1（query_order）`658ms` → 决策 2（query_logistics）`1301ms` → 首 answer`2498ms`。规划循环 3 次"决策→睡眠"串行（约 0.5—0.7s/次），首 token 前必须等完整规划链结束。

### 9.3 Token 消耗与成本超标

- 每现有脚本合格业务 2713 token（基准）/ 2718（稳定性）/ 2716（流式），超本机校准目标 ≤1000（生产 ≤2000）。
- 成本 5.43 元/合格业务（Mock 假设 2 元/千 token），远超本机校准目标 ≤0.1 元（该目标基于真实模型价，此处仅作口径演示）。
- token 膨胀机制（T00001 实测分解）：决策 1 携带 658 字符（329 token）→ 工具结果 JSON 原样回填历史（436 字符）→ 决策 2 涨到 1116 字符（558 token）→ 物流 JSON 再回填（458 字符）→ 决策 3 涨到 1600 字符（800 token）。规划循环内每次决策都完整携带 system prompt 与已累积的工具结果，且工具结果无压缩。

### 9.4 达标项

- E2E：非流式 P90 2.55s、流式 P90 4.79s，均满足实验室目标 ≤10s（本机校准 ≤5s）。
- 流式节奏：相邻字符事件间隔 P90 40.8ms，源于 Mock 固定输出节奏，只作校准，不作 TPOT 达标证据。
- 业务完成率 100%，结果合格率 99.81%—100%；工具选择与结果判定在 Mock 确定性模型下稳定。
- 客户端中断不拖垮服务，后续业务正常。

## 10. 结论与下一阶段待办

- 单 Agent 初版功能判定全部跑通，但尚未达到可验收状态。
- 待优化项（供第 20 讲回归验证）：① 规划循环串行导致 TTFT 超目标；② 工具结果无压缩回填导致 token 成本膨胀；③ SQLite 单连接跨线程竞态导致并发合格率掉点。
- 下一阶段（Multi-Agent，案例二）须复用同一需求、数据口径与验收方法，仅替换系统执行方式，以对比架构演化带来的性能差异。

### 11.3 M0 与 M5 差异解释（均非业务退化）

1. **答复与判定：零差异。** 同一 Mock 决策语义（MockProvider 按运行隔离随机状态，
   seed=42 序列一致），205 笔答复逐字一致、合格率一致。
2. **E2E 变大（mean 2089→3786ms）：口径变化，非性能退化。** v2 完整接口与流式
   共用单一运行循环，最终答复按 Mock token 节奏（40ms/片段）逐片段产出后再进入
   终态；该口径与 v1 流式接口一致（v1 正文流式 E2E P90 4.79s ≈ v2 P90 4.59s）。
   v1 非流式接口不经过逐片段输出，E2E 偏低。架构对比实验须同口径重测。
3. **估算 token 变小（477.0k→388.7k）：估算口径变化。** v1 每轮决策重复携带
   `tool_selection` 提示词全文（约 250 字符/轮）计入估算；v2 内部历史只携带一次
   查询与按调用 ID 关联的观察序列，JSON 兼容协议下由 Provider 在请求组装时注入
   提示词。两侧均为 `usage_source=estimated`，不代表真实模型用量。
4. **意图判定等价修正：** v1 决策在含工具描述的提示词文本上识别意图（“物流”字样
   使缺省意图落入 logistics_query）；v2 MockProvider 按原始问句判定时保留该等价
   缺省分支（见 `src/llm/mock_provider.py` 的 IntentDetector 说明），以保证与 M0
   基线工具序列一致。

### 11.6 Langfuse 真实上报验证（2026-09-13，自托管 4.35.0）

老板在 Langfuse Web 生成项目密钥后完成真实上报冒烟，过程中发现并修复三个问题：

1. **v4 摄取格式变更**：Langfuse v4 默认 `LANGFUSE_MIGRATION_V4_WRITE_MODE=events_only`，
   `/api/public/ingestion` 拒绝旧版 `trace-create/generation-create/span-create`
   事件；导出器载荷改为 v4 信封格式（每条事件 `{id, type, timestamp, body}`，
   事件字段入 `body`），并在服务端 `.env` 增加
   `LANGFUSE_MIGRATION_V4_WRITE_MODE=dual` 迁移桥（`docker-compose.yml` 同步
   增加该变量的传递条目，默认仍为 events_only），web/worker 重建后生效。
2. **207 多状态被误判成功**：v4 对逐条校验返回 HTTP 207 + `successes/errors`
   明细，旧导出器不解析响应体导致静默丢弃；已修复为逐条告警，
   全部被拒时上报记为失败。
3. **非流式路径事件缺投**：`arun` 原先只把内部模型调用事件交给导出器，
   工具事件与 done 终态缺失；已统一为与 `astream` 相同的事件分接。

修复后端到端验证（真实 HTTP 服务 → 真实 Langfuse）：

- 非流式（`/api/v1/chat/complete`）与流式（SSE）各一笔均完整入库：
  Trace 主体（input/output/status/stop_reason/evidence_kind/total_tokens/
  tags/sessionId）+ GENERATION（3 次决策 prompt token 176→392→620 递增可见、
  1 次 final_answer 含输出 token）+ SPAN（query_order / query_logistics，
  失败尝试标 ERROR）。

4. **Goodput**＝合格业务数 ÷ k6 实测总时长（B0 分母含预热段，约占总时长 1%）。
5. **工具覆盖率**为观测项，分母为 `expected_tools` 非空业务；<内部路径> §1 的 Tool Accuracy 为
   「正确工具选择数 ÷ 总选择数」，两者不可直接比较，本套件不设该阈值。
6. **成本**＝已知用量 × 假设单价 ÷ 合格业务数（本节三窗用量覆盖率均为 100%）。
7. **阈值**取自 <内部路径> §1 实验室目标（合格率 >90%、E2E P90 <10s、错误率 <0.5%），属假设值，待业务方校准。
8. **与 Python 脚本的口径差异**：C1 按档时长（1min/档），`capacity.py` 按档样本数；两者不直接混比。
