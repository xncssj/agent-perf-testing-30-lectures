# 客服工单系统性能分析手册（RESAR 七步）（公开脱敏版）

> 公开脱敏版：由案例内部资料裁剪而来，已移除实例 ID、IP、账号、密钥与内部路径。

> 版本：v1.2（2026-09-27 修订：对齐 09-26 全场景轮事实与问题清单 v1.0）
>
> 定位：第 14—20 讲七步分析的**人用执行手册**——「分析时先看什么、何时下钻、何时停止」。每步给出输入、判断顺序、常见误判、取证动作、产物与下一步交接；过程记录进性能分析底稿模板，正式结论回填压测报告模板。
>
> 口径依据（唯一来源，不在本手册另设数值）：目标契约（门禁三态、Goodput 分母、E2E 双口径）、性能测试方案 v1.1（负载量纲、运行资格准则 §4.4）、压测环境监控方案 v1.1 §6.1（问题→全局→定向映射）、取数与工具缺口清单（数据源状态）。
>
> 使用前提：分析对象是**一组可比运行**（如 B0＋C1＋S1 的同指纹集合），不是一个 Run ID；Mock 与真实 provider、流式与非流式、Python 与 k6 的读数不合并。

## 0. 先验运行资格（每步共用，未通过不进入分析）

按方案 §4.4 与底稿 A 页逐项核对：Run ID／场景／阶段、代码与数据指纹（commit、schema、`SEED`）、Mock/Provider 与流式模式、计量窗、各档样本量、环境变更、三态门禁与证据覆盖。另须显式两查：①**逐档样本量非零**——零样本档不得静默放行，应按 `INSUFFICIENT_SAMPLES` 判 `NOT_VERIFIED`（B2：09-25 场景链曾把 C1 level 5—50 五档零样本静默判过）；②**无外部信号中止痕迹**——k6 退出码 105/143/137 须人工复核三态，聚合器此前会把 SIGTERM 中止（09-25，退出码 105、仅 28 笔样本）错判 PASS（B1）。任一项缺失或运行被中止／受染：该轮按 `NOT_VERIFIED` 处理，保留现状与原因，只允许引用其「无效证据」身份，不引用其读数下容量结论。

## 1. 第一步：压力数据（第 14 讲）

- **输入**：上一窗的原始结果集——`manifest.json`、`summary/run.json`、逐档摘要（`*-levels.json`）、逐笔样本、事件与哈希；第 13 讲的数据质量说明。
- **判断顺序**：①逐档样本量与门禁三态 → ②逐档 Goodput、客户端 E2E P90/P99、合格率、成本曲线 → ③退化档（首个 SLO 不达标档＋衰减起始档，双记录）→ ④异常时间窗（曲线突变、失败簇、样本断档）。
- **常见误判**：跨档汇总分位数掩盖衰减；把 `NOT_VERIFIED` 当合格档；把 VU 档位当在线用户数；Mock 读数外推生产；把 2 分钟缩短版 s1 外推长稳结论（D1：s1 全部为 2 分钟缩短版、正式长稳未测，长时劣化证据不足）。
- **取证动作**：曲线读数与 `summary/run.json` 对数；异常窗标记到秒级并记录来源文件；分位字段缺失（如 `run.json` 无 p99）时登记取数缺口，不得当作 0 或不取（D2：09-26 轮 P99 未取，长尾验收项空缺）。
- **产物与交接**：业务曲线＋异常时间窗清单＋可检验假设候选列表（交第 15、17、18 步）。

## 2. 第二步：执行架构（第 15 讲）

- **输入**：第 14 步异常时间窗与退化档；系统三层架构与部署路径（方案 §6）。
- **判断顺序**：①把异常窗映射到「工单输入 → Agent 运行循环 → 工具/Provider → 存储 → 观测」路径上的节点 → ②区分被测路径与观测/施压自耗路径 → ③标注候选节点与其上游下游。
- **常见误判**：把架构风险评分当实测瓶颈；把观测栈占用算进被测系统容量。
- **取证动作**：在架构图上标异常映射（风险标记，不是结论）；核对部署指纹与运行窗内是否发生变更；观测栈自耗硬前置核查——Langfuse ClickHouse 摄取自耗曾达 5.4 核、loadavg 峰值 182/12 核致同机并发档读数不可用（B7），观测栈须与被测系统分离部署、压测窗关闭非必要上报，否则该轮读数按受染处理。
- **产物与交接**：带风险标记的架构图＋异常与候选节点映射（交第 16、17 步）。

## 3. 第三步：时间拆分（第 16 讲）

- **输入**：同一运行集合的任务计时与执行轨迹（`metrics(with_trace=True)`、Langfuse Observation、逐笔样本）；Langfuse 取数须钉版 4.45.1（浮动 tag 曾混入上游 4.46.0 致 MCP API 恒空，已回退钉版），且无 getTrace 单点查询接口，取数须绕行（B4）。
- **判断顺序**：①客户端 E2E 与服务端各阶段口径对照（`e2e_client_wall_ms` vs `e2e_server_ms`，两列不合并）→ ②按关键路径归因（排队、模型调用、工具执行、存储各占多少）→ ③Token 与成本随时间的分解。
- **常见误判**：并行 Span 耗时机械相加（重叠时间只算一次，按关键路径取值）；双口径混算分位；把 P90 代入 `L ≈ λ × W`。
- **取证动作**：同一 Task ID/Run ID 对齐客户端与服务端计时；并行段用关键路径法而非求和。
- **产物与交接**：时间与成本分解表＋「无法归因时间」显式标注（交第 17、18 步）。「无法归因时间」两条纪律：①节点级时延持平而墙钟增长时，差额即节点间排队/流式调度归因盲区，须显式标注并登记服务端请求级时间戳取数缺口（A2：09-26 阶段三 C1 首字 2000ms 门槛即被节点间排队/流式调度层击穿，L30 61.1%、L50 0%，可用并发约 20 VU/5.724/s）；②流式响应须分块打点，否则首答后的流式慢尾无法归因（A3：阶段三 b0 双峰，13.9% 笔 >5.5s，慢尾在首答之后的流式段）。

## 4. 第四步：全局观测（第 17 讲）

- **输入**：第 14 步异常窗、第 15—16 步候选路径；监控方案 §6.1 四类路径映射。
- **判断顺序**：①压测端（k6 序列按 `run_id` 过滤）→ ②应用终态与在途 → ③依赖（JVM/MySQL）→ ④容器与主机——每层只回答「这一层在异常窗内是否同步异常」。
- **常见误判**：单指标相关性当因果；面板均值替代分位；即时查询 k6 序列（结束即 stale，必须按窗范围查询）。
- **取证动作**：按监控方案 §6.1 表逐路径核对候选计数器；记录每层序列的时间窗与 `job`/`instance`；先核观测栈自耗硬前置——观测栈与被测系统同机时该层读数按受染处理（B7，Langfuse ClickHouse 摄取自耗 5.4 核/loadavg 峰值 182 案）；无法覆盖的层登记监控缺口。
- **产物与交接**：同期全局信号对照表＋疑似区域缩小结果＋监控缺口清单（交第 18 步）。

## 5. 第五步：定向验证（第 18 讲）

- **输入**：第 14 步假设候选、第 17 步疑似区域。
- **判断顺序**：①同一业务类型选正常、慢、失败三任务做轨迹/评测对照 → ②按异常类型触发定向数据（慢 SQL、线程栈、错误日志聚类，见缺口清单 §3）→ ③控制实验（固定其余条件只改一因，或降压复现）；先干净重跑逐位复现再下归因——09-25 首轮 s1 FAIL 曾误归因「init-host 中途变更污染」，干净重跑逐位复现后证伪（C5）；已验证案例锚点：共享连接并发腐坏（pymysql InterfaceError）即由错误日志聚类＋五证闭环定位（A1）。
- **常见误判**：单条慢 Trace 直接下结论；只看成功样本；定向工具常开影响读数。
- **取证动作**：定向命令单次执行、产物挂 `run_id` 归档；控制实验使用新 Run ID 并单列变化参数。
- **产物与交接**：每个假设的「已证实／已证伪／待验证」判定与证据位置（交第 19 步）。

## 6. 第六步：判断瓶颈（第 19 讲）

- **输入**：第 14—18 步同运行集合的全部证据。
- **判断顺序**：①按「压力现象 → 执行轨迹 → 同期计数器 → 机制 → 控制实验」五环检查每个候选 → ②五环齐才写「已证实」；缺环降级为候选 → ③多瓶颈按对目标的影响排序，写明证据强度与未排除因素。
- **常见误判**：无控制实验即宣称证实；把「CPU 高」等现象当根因；不给未排除因素清单。
- **取证动作**：逐假设核对五环；缺环项列「补什么证据、从哪里补」。
- **产物与交接**：瓶颈结论＋证据链＋边界（交第 20 步与报告）。

## 7. 第七步：优化回归（第 20 讲）

- **输入**：第 19 步瓶颈结论。
- **判断顺序**：①优化方案（对准机制，不碰口径）→ ②配对复测：新 Run ID、同业务集/负载/环境/口径、唯一改动 → ③四项复核：Goodput、P90/P99、质量、成本——任一回退不得宣称有效。
- **常见误判**：无配对复测宣称优化有效；复测条件漂移后对比；顺手改多处后归因单一改动。
- **取证动作**：配对表登记进底稿 C 节；条件不一致时如实声明不可比。
- **产物与交接**：配对结果与新基线，或「方案＋待验证项」交接后续窗口；正式结论回填压测报告模板。

## 8. 正常／慢／失败三任务对照法

定向验证与时间拆分共用：从同一运行、同一业务类型（同一 `expected_intent`/工单类）中各取一例，先对齐任务身份（Task ID/Trace ID），再逐段比耗时、工具选择、Token 与终态。差异段落即候选机制；三例不足以下结论时扩大取样并记录抽样方式。跨源逐笔对账依赖 `ticket_id`，k6 样本 tags 暂缺时对账降级为运行级并如实标注（B3）。

## 9. 何时下钻、何时停止

- **下钻条件**：全局计数器与业务异常落在同一时间窗，且候选路径唯一或可排序。
- **停止条件**：监控方案 §6.1 各路径的停止条件（定位到语句/等待点/饱和组件即停）；证据链五环齐即转入结论；工具不可达且无替代来源时，登记缺口并把该判断保持「待验证」，不硬凑。
- **升级条件**：需要外部权限（云端产物、数据库账号、剖析器安装）或触发新一轮运行时，列出请求项交窗口负责人，不在分析过程中擅自执行。
