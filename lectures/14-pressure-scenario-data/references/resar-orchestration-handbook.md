## 1. 混合架构总览：Workflow 把门、AI 出活、人拍板

压测项目的全部工作按「确定性」分层，对应三种处理方式：

| 层 | 内容 | 承载物 | 为什么 |
|---|---|---|---|
| **Workflow 把门层** | 压测启动/停止、指纹闸门、阶段隔离、熔断停跑、证据上传与回执、销毁防护 | `<实验脚本>` / `<实验脚本>` / fuse-controller / `<校验脚本>` / OSS readback | 确定动作要求稳定、可控、可追责，绝不交给 AI 自由发挥（红线：压测执行、写库、发布不进 AI 决策面） |
| **AI 出活层** | 压测统筹决策、七步分析的全部判断（曲线、架构映射、时间分解、观测对照、假设验证、瓶颈评审、回归方案） | 本手册定义的专家团（Sub Agent） | 输入不可预测、路径需探索的判断性工作，人写 SOP 指导而非硬编码 |
| **人拍板点** | ①压测启动与熔断后重启 ②配对复测发起 ③降断言类口径变更 ④瓶颈结论确认 ⑤报告对外发布 | 主 Agent 上报老板 | 高风险边界上设检查点，AI 是建议者不是执行者 |

专家团拓扑（执行窗 + 分析窗两段）：

```text
【执行窗】(k6 编排手册)                 【分析窗】(本手册)
k6-window-director ──收窗交接单──▶ S1 压力数据
  ├── A 发压                        ├──▶ S2 执行架构 ──┐
  ├── B 服务端与环境                 ├──▶ S3 时间拆分 ──┤
  ├── C 结果分析                    └──▶ S4 全局观测 ──┤
  └── D 业务监控                          ┌───────────┘
                                          ▼
                                    S5 定向 Trace+Eval
                                          ▼
                                    S6 瓶颈判定评审 ──(老板确认)──▶ R 报告
                                          ▼
                                    S7 优化回归 ──(复测人工拍板)──▶ 新基线
```

## 2. 五维度角色定义

每个角色由五个维度完整定义（对齐五维度定义法）：**职责边界**（管什么/不碰什么）、**工具白名单**（默认闭合，不存在的门走不出去）、**权限范围**（读写边界，跨角色走交接不走翻找）、**风险等级**（低=自动交接、中=主编复核、高=人拍板）、**输出契约**（结构化字段，下游验格式不猜语义）。完整角色卡见 `<内部路径>` 各文件的「五要素角色卡」节，此处为总表：

| 角色 | Sub Agent | 职责边界 | 工具白名单 | 风险 | 输出契约 |
|---|---|---|---|---|---|
| 执行窗统筹 | `k6-window-director` | 清单核对→授权→编排→熔断决策→收窗交接；不直接跑 k6 | <实验脚本>、SSH 只读、运行目录写 | **高** | 当窗结论段 + 收窗交接单 |
| S1 压力数据 | `resar-s1-pressure-data` | 验资格→曲线→异常窗→假设清单 H1..Hn | 只读产物 + prom_pull | 低 | 底稿 S1（curves/anomalies/hypotheses） |
| S2 执行架构 | `resar-s2-architecture` | 异常窗→节点映射、观测自耗核查、风险标记 | 只读架构文档 | 低 | 底稿 S2（anomaly_node_map） |
| S3 时间拆分 | `resar-s3-time-split` | 双口径对照、关键路径、Token/成本、盲区标注 | 只读 + lf_pull/prom_pull | 低 | 底稿 S3（key_path/unattributed） |
| S4 全局观测 | `resar-s4-global-observability` | 四层同期对照、疑似区域、监控缺口 | 只读 + prom_pull（范围查询） | 低 | 底稿 S4（layers/suspects/gaps） |
| S5 定向 Trace+Eval | `resar-s5-trace-eval` | 三任务对照、触发式定向证据、逐假设判定 | 只读 + lf_pull + 证据包 | **中**（主编复核） | 底稿 S5（hypothesis_verdicts） |
| S6 瓶颈判定 | `resar-s6-bottleneck-judge` | 五环证据链核验、排序、未排除因素 | 只读底稿与证据抽查 | **中**（老板确认） | 底稿 S6（chain_checks/ranking） |
| S7 优化回归 | `resar-s7-optimize-regress` | 方案、复测申请、四项复核、新基线声明 | 只读对数 | **高**（复测人拍板） | 底稿 S7（proposal/four_review） |

启用规则（成本纪律，"用多大的网捞多大的鱼"）：执行窗全编制按场景裁剪（见 k6 编排手册 §1 表）；分析窗 **S1—S4 是默认编制**，**S5—S7 仅在有异常窗/假设清单/已证实瓶颈时启用**——无输入不空转。

## 3. 七步 SOP（每步：输入 → 判断顺序 → 交接契约 → 已知限制 → 停止条件）

> 判断细则与误判清单统一见性能分析手册 v1.2 对应节；各步 Sub Agent 角色卡含完整命令级指引。

### S1 获取业务压力场景数据（第 14 讲）

- **输入**：收窗交接单（run_set/指纹/计量窗/产物路径）；原始产物 `summary/<运行摘要>`、`raw/k6-*`、`<运行清单>`。
- **判断顺序**：先验运行资格（样本量非零、无中止痕迹、三态如实）→ 逐档 Goodput/E2E P90/P99/合格率/成本曲线 → 退化档双记录 → 异常时间窗（标记到秒级+来源文件）→ 假设清单 H1..Hn。
- **交接**：底稿 S1 → S2/S4/S5；`hypotheses[].id` 是后续所有步骤的线索主键。
- **已知限制**：P99 缺字段（D2）、tags 无 ticket_id（B3）、s1 缩短版（D1）、Mock 不外推（D5）。
- **停止**：异常窗标记完成且假设清单成稿；不下钻。

### S2 分析 Agent 执行架构（第 15 讲）

- **输入**：S1 底稿异常窗；架构底图四张（`<内部路径>`：核心链路时序/应用架构/阿里云部署/压测架构）。
- **路径锁定前置**：读取链路核实与勘误，核对本运行原始摘要的 `board.fingerprint.gateway`、逐笔业务 URL 与请求选择代码；`manifest.target.base_url` 只提供 Agent 地址，不能单独证明业务直压。阶段 1 是否经过 Java，另核对 `java_service_enabled` 与工具注册分支；阶段 2/3 不继承阶段 1 的数据路径。证据缺失时标未验证，禁止沿用被撤销的历史架构前提。
- **判断顺序**：异常窗→路径节点映射 → 被测路径与观测/施压自耗区分 → 观测栈自耗硬前置核查（B7）→ 运行窗部署变更核对 → 候选节点风险标记（先验标记非实测结论）。
- **交接**：底稿 S2（风险标记架构图 + `anomaly_node_map`）→ S3/S4。
- **停止**：映射表成稿；无异常时产出空映射并注明。

### S3 拆分端到端任务时间与业务时间（第 16 讲）

- **输入**：同一运行集合逐笔样本、Langfuse Observation、S2 候选节点。
- **入口范围**：业务经统一网关时，客户端 E2E 还包含网关及前端代理；Span 覆盖之外的时间保留为未归因。网关日志上游是阶段前端，不能把其耗时等同 Agent 服务端 E2E，也不以聚合分位数相减代替逐笔分解。
- **判断顺序**：`e2e_client_wall_ms` vs `e2e_server_ms` 双口径对照（不合并）→ 关键路径归因（排队/模型/工具/存储/调度；**并行 Span 不求和**）→ Token/成本分解 → 无法归因时间显式标注（A2 排队盲区、A3 流式慢尾条款）。
- **交接**：底稿 S3（时间瀑布分解表，逐类别）→ S4/S5。
- **已知限制**：B4 无 getTrace（分页绕行）、B3 对齐降级、流式指标仅 stream_benchmark 口径。
- **停止**：分解表成稿，每段有证据来源或显式「无法归因」。

### S4 全局可观测性分析（第 17 讲）

- **输入**：S1 异常窗、S2 候选与受染核查、计量窗时刻。
- **入口与依赖核对**：k6 与网关共驻控制机，分机发压不能排除入口资源竞争；同步查看控制机水位与网关日志。阶段 1 Java 开关开启时，订单、物流对应 Java/JVM/MySQL 是路径内候选；无同期异常只能说明当前指标未发现异常，不能根据旧底图将该层排除。
- **判断顺序**：观测自耗前置 → 四层逐层同期对照（k6 按 run_id 范围查询 → 应用终态/在途 → JVM/MySQL 依赖 → 容器/主机），每层只答「异常窗内是否同步异常」→ 疑似区域缩小与排序 → 监控缺口登记。
- **交接**：底稿 S4（`layers`/`suspect_regions`/`monitor_gaps`）→ S5。
- **停止**：对照表成稿；相关性不作因果。

### S5 定向 Trace 与 Eval 分析（第 18 讲）

- **输入**：S1 假设清单、S4 疑似区域、慢/失败任务候选。
- **判断顺序**：正常/慢/失败三任务对照（对齐任务身份；B3 时降级为类别+时间窗并标注）逐段比**耗时+工具选择+Token+终态质量（Eval）**，差异段即候选机制 → 触发式定向证据（单次执行、挂 run_id）→ 逐假设判「已证实/已证伪/待验证」+ 反证检查 → 控制实验需新 Run 时出申请单（人拍板）。
- **交接**：底稿 S5（`hypothesis_verdicts`，经主编复核）→ S6。
- **停止**：假设清单全部有判定；无输入时如实产出「S5 不适用」。

### S6 判断 Agent 性能瓶颈（第 19 讲）

- **输入**：S1—S5 五份底稿（同 run_set，可比性复核前置）。
- **判断顺序**：五环证据链逐假设核环（压力现象→执行轨迹→同期计数器→机制→控制实验）→ 五环齐判「已证实」，缺环降「候选」→ 按对 SLO/Goodput 影响排序 → 未排除因素清单。负结论合法：无可证实瓶颈时如实交付缺环清单。
- **交接**：底稿 S6（`chain_checks`/`ranking`/`unexcluded_factors`），经主编复核 + **老板确认** → S7 与报告。
- **停止**：每个假设有五环记录；不放水放宽环标准。

### S7 确定方案并回归验证（第 20 讲）

- **输入**：S6 结论（已证实瓶颈或候选清单）、原运行集合、（若有）复测轮。
- **判断顺序**：优化方案对准机制（不碰口径、不降断言）→ 配对复测申请（新 Run ID、唯一改动、成本估算；**人拍板后**才由执行窗跑）→ 四项复核（Goodput/P90P99/质量/成本，任一回退不得宣称有效）→ 新基线声明或如实「不可比/待复测」。
- **交接**：底稿 S7 → 报告（R）。

## 4. 协作机制

### 4.1 结构化交接

- 交接物是**步骤底稿**（`reports/底稿-<run_set>-S<N>.md` + 同名 `.json`），md 写分析叙述、json 是机器可验的字段契约；各步 schema 见 `<内部路径>` 对应角色卡。
- 下游开工**先验上游 schema**：缺必需字段（如 S1 缺 `anomaly_windows`）→ 停下报主编，不带着错误数据往下走。
- 底稿字段 `confidence`（0—1）与 `unknowns[]`（缺什么/影响什么/从哪补）是必填元数据——低置信度触发主编重派或降级处理，对齐驾驭体的 confidence/reasoning 机制。

### 4.2 审批路由（三级）

| 风险 | 动作示例 | 流转 |
|---|---|---|
| 低 | S1—S4 只读分析与底稿交接 | 自动通过，主 Agent 验 schema 后转交 |
| 中 | S5 假设判定、S6 瓶颈结论 | 主编复核后进入下游；S6 另需**老板确认**进报告 |
| 高 | 压测启动/重启、配对复测发起、口径降断言、报告发布 | 上报老板拍板，AI 只出申请单与建议 |

### 4.3 降级路径（故障不扩散）

- **数据源级**：MCP 通道不可达/缺页 → 该判断标 `no_data` + 登记 `monitor_gaps`，保持「待验证」，不用替代来源硬凑。
- **角色级**：某步产出缺环 → 下游降级消费（如 S6 收到全「待验证」→ 出负结论版）。
- **重派**：主编可对 S1—S4 重派（补数据、换口径），同一 run_set 重派上限 2 次，超限升级人工。
- **整体降级**：分析链路不可用时，执行窗照常独立运行（两段解耦），分析欠账如实登记。

### 4.4 审计留痕

每步底稿入 `<内部路径>`；MCP 调用留痕在 `<内部路径>`（prom_pull/lf_pull 输出）；证据引用必须落文件路径；与 OSS 回执、`evidence/` 证据包对账。任何一次结论可回放：「哪份底稿、哪些证据、谁复核、谁拍板」。

## 5. 主 Agent 派发协议

会话主 Agent（或 `k6-window-director` 收窗后）按以下顺序派发分析团：

1. 固定 run_set：调 `<内部路径>` 的「固定同一组实验」七要素，产出收窗交接单。
2. 派 S1（必派）→ 验 schema → 有异常窗则派 S2、S3、S4（可并行，输入互不依赖 S1 之外的上游）。
3. S4 产出疑似区域 + S1 有假设清单 → 派 S5；主编复核判定。
4. 派 S6 汇总评审（输入五份底稿）；结论经老板确认后派 S7 或进报告。
5. 每次派发消息必须携带：run_set、上游底稿路径、本步数据源路径、底稿输出路径、当轮口径声明。

## 6. Sub Agent 资产索引与调用方式

定义实体：`<内部路径>`（8 个，frontmatter 含 `name/description/tools`）。主 Agent 读取角色卡后按路由调用，例如：

- 执行压测窗口 → `k6-window-director`；
- 收窗后第一步分析 → `resar-s1-pressure-data`；
- 全局观测对照 → `resar-s4-global-observability`。

角色卡引用本手册与性能分析手册的相对路径均以仓库根为基准；若工具运行环境无法解析实体外的引用，把两份手册路径随派发消息显式带上。

压测协作体系补充（2026-09-29 起）：008 规格包 另建了准备/执行/收尾 10 个 `pt-*` 协作角色卡（同在 `<内部路径>`）。其中收尾角色（`pt-defect-recorder`、`pt-report-drafter`）消费本手册 S1—S7 的底稿与限制条款；`pt-window-analyst` 产出的窗口包由窗口统筹按 §5 固定 run_set 后交给 S1。七步判断逻辑与启用条件仍以本手册为准，`pt-*` 角色不改写。

### 7.2 勘误：Langfuse 压测窗上报状态表述（2026-09-30，问题清单 C7）

§7 实录 S2 行「Langfuse 压测窗上报状态核对通过（clean）」与压测前检查清单 C 节旧文「压测计量窗关闭上报」**均与运行实况不符**，按 §8 维护约定以本节勘误，不改写上文原文：

2. **「clean」的本意与局限**：该表述指「观测栈分离部署核对通过、压测窗上报链路无报错」，未包含「上报开关状态」的核对，当时未发现口径差异；第二轮预压 S2 据实测判 **B7 contaminated（范围限定）**——观测栈物理分离（obs-stack 独立机）成立，业务读数与门禁不受染，进程内 exporter 开销未量化。
