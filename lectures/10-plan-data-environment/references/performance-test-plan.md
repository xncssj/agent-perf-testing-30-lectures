# 客服工单系统 Agent 性能测试方案（公开脱敏版）

> 对应第 10 讲正文引用的案例方案 v1.2。公开版保留目标、指标、场景、数据、环境、验收六件套与执行准则；实例 ID、IP、账号、密钥、余额、内部路径和逐笔原始产物已移除。
>
> 方案中的绝对值均为实验室口径，不能直接外推生产。

## 1. 背景与目标

客服工单系统贯穿三个阶段：Single Agent、Multi-Agent、Workflow/Flow + RAG。业务口径统一为“查询并答复指定订单的配送进度”，性能测试对象是端到端业务，不是单个 HTTP 接口。

目标定位为“性能验证为主、性能调优为辅”：先验证各阶段在目标负载下能否给出通过／不通过结论，压测暴露的问题再做最小闭环优化。

目标：

1. 建立三阶段各自可信的性能基线，带版本指纹与口径标注。
2. 给出容量结论：目标业务负载下的合格率、Goodput、时延分位与退化拐点。
3. 暴露失稳形态：循环／重试放大、队列堆积、级联故障与恢复完整性。
4. 验证性能、质量、成本与安全的联合门禁。

非目标：真实模型服务商的 SLA 验证、前端页面性能、观测栈自身性能。

## 2. 压测范围

| 阶段 | 被测对象 | 重点 |
|---|---|---|
| 阶段一 Single Agent | 单 Agent 运行循环（决策→工具→答复）、订单／物流／知识库工具 | 基线、容量、稳定性 |
| 阶段二 Multi-Agent | Supervisor 编排、扇出、熔断、恢复 | 并发放大、降级、恢复 |
| 阶段三 Workflow/Flow + RAG | 显式 Flow 节点与边、RAG 检索、联合门禁 | 路径覆盖、首字、质量门禁 |

边界外只监控或使用 Stub：Trace 上报链路、前端工作台、真实模型 provider。

## 3. 四个负载量纲

| 量纲 | 定义 | 案例取值 | 性质 |
|---|---|---|---|
| 在线用户数 `U` | 可同时打开会话的用户规模 | 50 | 假设，待业务方校准 |
| 平均业务到达率 `λ` | 每秒业务笔数，`λ = U × r` | 50 × 1/600 ≈ 0.083 业务/秒 | 假设平均到达率 |
| 计量窗在途业务数 `L` | 同一计量窗内已开始未完成的业务数 | 未实测 | 需用同窗停留时间交叉估算 |
| k6 虚拟用户数 `VU` | 施压脚本的闭环并发档位 | 1—50 | 执行参数，不是在线用户数 |

约束：

- `VU` 不能当作 `L`，也不能据此写“可服务 50 个在线用户”。
- P90 不得代入 `L ≈ λ × W`；该式只适用于相对稳定、同窗口、同条件的平均停留时间。
- 容量结论统一用 Goodput（合格业务/秒），并注明四级判定与时延 SLO 口径。

## 4. 执行准则

### 4.1 启动准则

1. 判定逻辑自测通过。
2. 数据与代码指纹固定：数据 schema、条数、随机种子、代码提交号、依赖版本写入当窗记录。
3. 口径确认：模型提供方、流式开关、计价假设写入实验指纹。
4. 观测链路就位：指标可抓取，需要 Trace 的窗口确认上报可用。
5. 施压机余量满足要求；同机压测必须标注同机口径。
6. 计量窗内禁止并行部署、禁止经控制入口做维护操作。

### 4.2 结束准则

1. 场景执行完毕，逐笔产物、聚合读数、当窗记录齐全。
2. 合格／失败业务逐条有终态，失败业务保留可回溯。
3. 实验记录已更新，环境已恢复。

### 4.3 暂停与再启动

任一条件触发即暂停：

- 错误率连续 2 分钟 > 5%。
- 合格率较同档基线下降 > 5 个百分点。
- 服务端非正常终态计数持续上涨。
- 单位时间 token 消耗超过同档基线 2 倍。
- 环境被变更，包括依赖升级、数据集重生成、他人同机作业。

再启动前必须定位原因、记录处置，并确认环境恢复稳定 10 分钟。

### 4.4 运行资格

只有通过运行资格检查的数据才能进入分析与容量结论。检查项包括：Run ID、场景与阶段、代码与数据指纹、模型与流式口径、计量窗、各档样本量、环境变更记录、三态门禁与证据覆盖。

被中止、被并行操作污染或证据缺失的轮次按 `NOT_VERIFIED` 或无效证据处理，不把局部有效档外推为完整容量曲线。

## 5. 指标与阈值

| 指标 | 实验室目标 | 场景 | 口径 |
|---|---|---|---|
| TTFT P90 | ≤ 1.5 s | 流式基准／容量 | 仅真实流式实测有效 |
| TPOT P90 | ≤ 80 ms | 流式 | 需 token 边界证据 |
| E2E 业务时延 P90 | ≤ 10 s | 全场景 | 门禁只认客户端墙钟 |
| 阶段三首字 P90 | ≤ 2 s | 阶段三 | 服务端指纹 |
| 业务合格率 | ≥ 90% | 全场景 | 四级判定 AND 语义 |
| 工具选择准确率 | ≥ 95% | 基准／容量 | 按阶段口径 |
| 错误率 | ≤ 0.5% | 全场景 | 请求级失败 |
| 成功业务成本 | 以基线校准 | 基准／容量／长稳 | 合格业务为分母 |
| 长稳末段劣化 | ≤ 20% | 稳定性 | 对比预热后首段 |
| 水位系数 | ≥ 2 | 容量 | 最大稳定 Goodput ÷ 目标 Goodput |

门禁结论只有 `PASS`、`FAIL`、`NOT_VERIFIED` 三态。证据缺失、熔断或中止的窗口一律 `NOT_VERIFIED`，不得当作通过；零样本档必须显式标记，禁止静默放行。

分位数按稳态档内统计；跨档汇总的 P90 不用于阶梯场景。面板平均值不能替代分位数。

## 6. 环境口径

| 口径 | 用途 | 结论边界 |
|---|---|---|
| 本机自托管：本地服务 + 本地库 + Mock | 开发冒烟、脚本自测 | 不能作为验收容量 |
| 云端四机隔离环境 | 正式压测窗口取证 | 可出压测环境结论，仍须标注 Mock 与链路前提 |

正式窗口的四机角色、网络分区与隔离要求见[云资源清单](cloud-resource-ledger.md)。

## 7. 实施红线

1. Mock 数据不得写成生产结论；合成口径与实测口径不得混表。
2. 压测只读业务快照，写操作不进入压测场景。
3. 真实 provider 密钥只经环境变量注入，不入库、不打印。
4. 施压与被测同机时，高并发档必须标注“同机执行”。
5. 正式容量结论应在施压与被测分离的环境中复核。

## 8. 场景设计

| 场景 | 目的 | 关键约束 |
|---|---|---|
| B0 基准 | 获取基线、暴露基础问题 | 工单全量轮换，固定输入分布 |
| B0s 流式基准 | 采集真实 SSE 的 TTFT／TPOT | 非流式不合成流式指标 |
| C1 容量阶梯 | 找退化区间与容量上限 | 每档“稳定 + 计量”，逐档独立摘要 |
| S1 长稳 | 暴露长时间运行问题 | 时长按业务积累量 ÷ Goodput 回填 |
| E1 流量变化 | 验证突发与骤降 | 两种模式独立运行 |
| E2 多轮上下文 | 验证轮次增长影响 | 轮数与增长步长固定 |
| recovery | 验证故障后恢复 | 恢复后使用新 Run ID 二次加压 |

执行纪律：

- 阶梯加压不回退重跑，触发暂停条件除外。
- 前几档 Goodput 应随并发近似正比增长；首档即退化先查压力是否到位。
- 退化判定记录两个值：首个 SLO 不达标档，以及时延／合格率开始衰减的档位。
- 容量结论只引用逐档摘要，跨档汇总仅作趋势展示。
- 模糊／异常工单按预期行为判定，不剔除；失败业务保留。

## 9. 数据准备

- 单一事实源：工单、订单、物流、知识库快照统一存放，禁止散落。
- 生成式、不手改：数据由脚本和固定种子生成，重复生成结果一致。
- 有版本、有清单：数据集带 Schema 版本与 MANIFEST，写清文件条数、字段含义、阶段消费关系。
- 跨版本不比较：数据集变化后旧基线作废。
- 输入按分布轮换，不能只抽标准工单刷漂亮曲线。
- 装载核对与质量核对并列：文件指纹对得上，不代表服务已装载；装载成功，也不代表引用与判定字段对得齐。
- 检查项包括：工单引用的订单／物流是否存在、预期事实与快照是否一致、模糊／异常工单是否按预期行为判定。

数据版本、构成与字段字典见[数据清单](test-data-manifest.md)。

## 10. 版本指纹

每轮至少记录六组指纹：

1. 数据：schema、条数、随机种子。
2. 代码：提交号与分发归档哈希。
3. 模型、Prompt、工具与流式：提供方开关、流式开关、Mock 时延参数。
4. 依赖与业务接口：运行依赖、订单／物流快照版本、API 契约版本。
5. 服务指纹：服务自报版本与 SLO 门槛。
6. 运行身份：Task ID、Run ID、Trace ID、场景、阶段、时间窗。

模型、Prompt 或链路变更后，必须重跑基线。

## 11. 成果输出

过程性产物每窗归档，不进入公开仓库：逐笔 JSON、当窗记录段、熔断与暂停记录。

可入库产物：实验记录、方案、检查清单、报告。报告中的容量、稳定性、异常分别给出通过／不通过结论，并带口径与指纹前提；每个上限附资源、配置或设计证据。

## 12. 风险与缺口

| 风险／缺口 | 影响 | 处置 |
|---|---|---|
| 负载模型 U／r 为假设 | 容量目标与负载形态 | 首轮基线后由业务方校准 |
| 无正式 SLA | 判定依据 | 用实验室目标先跑，基线后书面确认 |
| 真实模型时延／成本未复采 | 结论外推 | 单独安排真实 provider 冒烟与复采 |
| 长稳时长不足 | 验收证据 | 按业务积累量公式补足 |
| 版本指纹漂移 | 跨轮不可比 | 每窗记录，变更即新口径 |
| 同机压测互相干扰 | 读数受染 | 空跑自检，结论标注同机 |
| 观测栈自耗 | 读数不可用 | 四机分离，必要时关闭上报 |

## 13. 执行顺序

1. 判定自测。
2. B0 基线：冷启动与普通基准分开运行，各自使用新 Run ID。
3. B0s 流式基准。
4. C1 容量阶梯。
5. S1 长稳缩短版。
6. 阶段二扇出、级联、恢复。
7. 阶段三路径、RAG、门禁。
8. E1 流量变化与 E2 多轮上下文。
9. 异常场景。
10. 更新实验记录并撰写报告。
