# 性能需求表

参考课程第 08 讲“先摸业务底，别急着写指标”中的“业务底数表”，以及“本讲交付：两张表”中的“性能需求表”。使用说明见[本讲说明](../README.md#使用方式与证据状态)。

## 业务底数表

先回答“谁在用、量多大、人工现状、业务目标、失败影响”，再写指标。示例值取自客服工单案例的业务需求文档，换成自己的项目时逐行替换。

| 要摸清的问题 | 示例答案 | 对性能需求的意义 | 本项目填写 |
|---|---|---|---|
| 谁在用 | 终端用户在 Web/App 咨询；人工客服接管转接工单 | SLO 对用户体验负责，不是对接口负责 |  |
| 量有多大 | 日均工单 5000+，其中 60% 是订单物流咨询 | 主力业务量决定测试场景的构成比例 |  |
| 人工现状 | 平均响应 5 分钟；单客服 ¥8000/月；满意度 75%；人工处理 200 单/人/天 | “省”和“快”的基准线都从这儿算 |  |
| 业务方目标 | Agent 自动处理 60% 常见问题；平均响应压到 30 秒内；人力成本降 40% | 业务承诺，SLO 从它倒推 |  |
| 失败影响 | 答错订单状态或物流位置，用户投诉、转人工，信任归零 | “准”是红线，不是优化项 |  |

**单位与分母先写清。** 人工单笔成本按“月人工成本 ÷（月工作日 × 人均日单量）”计算：示例 ¥8000 ÷（21 × 200）≈ ¥1.9/单，但这只是工资口径下限。月工作日、成本口径（是否含社保与管理分摊）、坐席利用率未提供时，人工单笔基线记为“待回填”，不得当成已完成。

业务高峰系数、用户活跃比例同样可能缺失。缺失项留空并写明找谁回填，不要用拍脑袋数字占位。

## 性能需求表

需求表只写“要什么”。目标值、测量入口和证据状态留给 SLO 卡片。

| 字段 | 示例内容 | 证据状态 | 本项目填写 |
|---|---|---|---|
| 业务背景与痛点 | 日均工单 5000+、60% 为订单物流咨询；人工平均响应 5 分钟、单客服 ¥8000/月、满意度 75%、人均 200 单/天 | 业务需求文档已定 |  |
| 用户角色 | 终端用户（Web/App 咨询）；人工客服（接管转接工单） | 已定 |  |
| 工单构成 | 245 条六类用例（schema v2.1.0、SEED=42），关联 173 条订单快照、158 条物流轨迹快照 | 已入库、版本化 |  |
| 业务高峰 | 高峰系数暂缺 | 待业务方回填 |  |
| 失败影响 | 答错订单状态或物流事实，用户投诉、转人工、信任归零 | 已定；事实错误逐笔复核门禁待实现 |  |
| 业务目标 | 自动处理 60% 常见问题；平均响应 30 秒内；人力成本降 40% | 业务承诺，SLO 由此倒推 |  |
| 验收判定规则 | 红线 / P0 / P1 顺序判定；风险接受只对 P1 偏差开放，红线与 P0 失败不接受 | 规矩已立，三方确认记录待签 |  |

## 判定边界

- 形容词不是需求。“快、稳、准、省”每一行都要落到指标、目标值、统计窗口、数据集和证据位置。
- 没有回填、没有三方确认的行，不许写成对外承诺。
- 本表是需求契约，不是压测结果；示例数字只用于说明写法。
