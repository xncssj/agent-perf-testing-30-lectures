## 1. 结论速览

1. **s1/e1 的 FAIL 是真阳性，门槛无误报、无需校准**。根因是被测应用缺陷：`Database` 数据访问层全程共用一条 pymysql 连接，并发下协议腐坏后黏性失效。
2. 原「s1 被 init-host 中途变更污染」的归因**证伪**：干净重跑与原轮逐位复现（合格率 9.89% vs 9.88%，中位时延同为 1669ms），缺陷是确定性的。
3. **缺陷已修复并验证闭环**（v1.1）：线程本地连接方案上线后，s1 合格率 9.88%→**99.05%**（P90 1673→3378ms 回到健康形态）、e1 spike/drop 各相位 **100%**——修复前后同场景对照见 §2。
4. **c1 的原 PASS 无效**：k6 于 level_1 52% 处被外部 SIGTERM 中止（退出码 105，仅 28 笔样本），聚合器未识别信号中止仍判 PASS；level 5–50 五个档位零样本也未触发 `INSUFFICIENT_SAMPLES`。修复后两次完整重跑均被并行工作流的环境操作打断（§2 c1 行），但 L20/30/50 计量窗已证 100% 合格、P90 平直 ≈3375ms——**有效 c1 证据待静默窗口补跑**（约需 20 分钟独占）。
5. 有效低并发结论：b0（1 VU 合格率 99.0%，健康全链路 P90 3376ms）与 e2（10 轮串行 100%）。
6. 修脚本：<实验脚本>/deploy-role.sh 三处「`$变量` 后紧跟多字节字符」在 UTF-8 locale + `set -u` 下触发 unbound variable（含一次退出码失真为 0），已改 `${VAR}` 形式（对应仓库规则 `<内部路径>`「Shell 提示文本含非 ASCII 字符时变量引用一律写成 `${VAR}`」，本次为补应用漏点）。

## 3. 根因：共享 pymysql 连接的并发腐坏

### 3.1 缺陷位点

`<内部路径>` 的 `Database.__init__`：

```python
self._conn = _MysqlConn(_connect_mysql(mysql))
```

整个应用生命周期只建一条 MySQL 连接，全部工具（订单/物流/知识库检索）与管理端（登录/会话）共享它。PyMySQL 连接**非线程安全**：FastAPI 同步端点在线程池并发执行，harness 工具池提供 20 个并发工位，两个工具调用叠在同一条 socket 上时报文交错，MySQL 协议流错乱，PyMySQL 抛出 `pymysql.err.InterfaceError: (0, '')`；此后该连接的协议状态永久损坏，**所有后续使用方快速失败**——直到容器重建才会恢复新连接。

### 3.2 证据链（五证闭环）

| # | 证据 | 来源 | 指向 |
|---|---|---|---|
| 1 | 劣化窗口运行终态由 `failed/tool_failed` 主导（如 s1 十分钟窗 `tool_failed` 增量 6723） | Prometheus `sum by (status, stop_reason) (increase(agent_run_terminal_total[10m]))` | 工具层批量失败 |
| 2 | 活容器日志实抓 `pymysql.err.InterfaceError: (0, '')` 异常栈 | sut-agent `docker logs cs-agent-python` | DB 连接协议损坏 |
| 3 | `harness_tool_calls_inflight=0` 而 `agent_runs_inflight=21`：在途运行很多、在途工具调用为零 | business.ndjson / Prometheus | 工具调用瞬间失败，未进入执行池；`tool_overload=0` 排除槽位拒绝 |
| 4 | MySQL 侧完全健康：`max_connections=151`、`Max_used_connections=8`、`Aborted_clients=3`、`wait_timeout=28800` | dep-services `SHOW VARIABLES/STATUS` | 排除服务端杀连接/连接数打满 |
| 5 | 双时延指纹 3370ms vs 1670ms；劣化后回落 1 VU 仍 100% 失败（e1 post/low 相位 0/13） | k6-summary 分相位统计 | 短路响应跳过工具执行；连接黏性损坏不自愈 |

### 3.3 触发规律（与全部场景吻合）

- **不触发**：b0（1 VU 串行化）、e2（单 VU 逐轮）——请求从不重叠，共享连接无竞争；
- **中途触发**：s1（10 VU 持续）——前 ≈800 笔合格（约 4 分钟）后发生首次报文叠写，此后 7300 笔全灭；
- **瞬时触发**：e1 spike/high（20 VU 阶跃）——数秒内叠写，整相位 0/260；
- **黏性**：每场景前 `deploy-role` 重建容器获得新连接，故 e2 能在 e1spike 之后恢复全好；同一场景内相位回落后不恢复（e1 post/low 全灭）。

### 3.4 波及面

被测前端管理端与本代理共用 `Database` 实例，共享连接损坏后前端 `/api/v1/auth/login` 同步 500（外网访问验收时的页面可达性不受影响，登录功能在连接损坏期间不可用）。影响面经核实**仅限阶段一**：阶段二（multi-agent）数据层为只读 SQLite（无 pymysql 依赖），阶段三无独立数据层，均不受本缺陷影响。

## 4. e1 门槛校准结论

1. **`QUALIFIED_RATE_MIN=0.90` 工作正常，不调整**。e1 两轮 `error_rate=0`、P90≈1.68s（SLO 的 1/6）——若只看性能两项会误判「完全健康」；业务合格率是唯一报警项，门禁设计的价值实证。
2. 小样本提示（非缺陷）：e1spike `phase:pre` 仅 7 笔样本，1 笔失败即 0.857<0.90 触限。该相位是基线对照性质，解读时注意样本量；契约的 `INSUFFICIENT_SAMPLES` 目前无最小样本数定义，可作为后续契约增强项（不在本轮改动范围）。
3. **聚合器缺口一（须修）**：k6 被信号中止（退出码 105，`received a 'terminated' signal`）后聚合器仍判 PASS。契约 §5 规定 aborted 窗口不可判 PASS（应 NOT_VERIFIED），实现只识别了自身熔断/中止标志，未覆盖执行器信号退出。
4. **聚合器缺口二（须修）**：c1 level 5/10/20/30/50 五档零样本未触发 `INSUFFICIENT_SAMPLES`，「有阈值无样本」被静默放行。

## 5. 干净重跑与归因修正

第一轮 s1 结束后曾执行 `init-host` 基线加固（时间线 30），当时将 s1 FAIL 归因为「基线中途变更污染」。本轮重跑条件：全新容器连接（`deploy-role` 重建）、`preflight` 全绿（四节点健康、真实工单 T00001 通过）、全程无任何中途变更。结果与第一轮逐位一致：

| 指标 | 第一轮（0459Z） | 干净重跑（0700Z） |
|---|---|---|
| 合格率 | 9.88%（800/8100） | 9.89%（801/8099） |
| 错误率 | 0 | 0 |
| 中位墙钟 | 1669ms | 1669ms |
| 运行终态主导 | tool_failed | tool_failed |

结论：**确定性并发缺陷，与 init-host 无关**。Mock 时序（SEED=42）与 VU 调度的确定性使两次运行在几乎相同的请求数处发生首次叠写。

## 6. 修复建议与复跑清单

### 6.1 被测应用修复方向（待老板决策后实施）

| 方案 | 改法 | 评价 |
|---|---|---|
| A 短连接 | 每次数据操作新建/关闭连接 | 改动最小；Mock 场景 DB 操作频率低，开销可接受；真实模型下每请求多 1–2 次握手 |
| B 连接互斥 | 保留单连接，操作级加锁（或线程本地连接） | 吞吐无损；串行化 DB 访问，DB 不再是并发瓶颈假象 |
| C 连接池 | 引入 SQLAlchemy/自建池：`pool_size≈tool_workers`、`pool_pre_ping`、`pool_recycle<wait_timeout` | 最工程化，三阶段共享层一次到位；改动最大 |

教学口径提示：该缺陷是「共享可变资源无同步」的典型性能反模式（连接被当作无状态单例），对本专栏具有正面案例价值。

### 6.1.1 修复实施记录（2026-09-25，老板决策：修复）

采用**线程本地连接 + 连接级错误弃旧重建**方案（上表 B/C 的折中，未引入新依赖）：

- `<内部路径>`：`_MysqlConn` 改为 `threading.local` 代理——每线程惰性建立独享连接；`execute` 遇 `InterfaceError`（含 `(0,'')`）或 2002/2003/2013 时弃旧连接、重建并重试一次；`commit`/`executescript` 路由到线程本地连接。`execute/commit` 对外接口与共享连接时代完全一致（这也是不选外置连接池的原因：连接池会破坏「execute 返回游标 + 包装层 commit」的配对语义）。
- 原 `_connect_mysql` 拆为 `_mysql_bootstrap_database`（建库，进程内一次）与 `_new_mysql_connection`（线程本地建连工厂），启动竞态重试口径不变。
- SQLite 路径不动：CPython sqlite3 序列化模式下共享连接跨线程安全，阶段二本就是只读 SQLite，不受影响。
- 本地桩测试三场景通过：8 线程×50 操作每线程恰好 1 条连接；坏连接注毒后自动重建重试成功；非连接级错误原样上抛。
- 云端部署采用外科手术式更新：仅 `scp` 该文件至 sut-agent 案例路径（整包推送会混入并行工作流未完成的鉴权实施改动），删除 `cs-agent-python:1.0.0` 镜像后经 `deploy-role.sh sut-agent 1` 重建，容器内文件哈希与本仓一致（`a1445b47…`）。
